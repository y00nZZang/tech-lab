# gRPC Kubernetes 로드밸런싱 1차 실행 결과

## 실행 시각과 환경

- 날짜: 2026-08-18 (Asia/Seoul)
- Docker Desktop: 29.4.0
- kind: 0.32.0
- Kubernetes server: 1.36.1
- 최초 실행 때 사용한 kubectl client: 1.34.1
- 아키텍처: macOS arm64, 단일 control-plane node

최초 실행의 kubectl은 server보다 minor version이 2 낮아 공식 지원 범위 경고가 있었다. 리소스 적용과 실행은 성공했지만 재현 스크립트는 이후 kubectl 1.36.1을 내려받도록 수정했다.

## 결과 요약

| 경우 | 요청/동시성 | Pod별 요청 수 | 처리량 | latency p50/p95 | queue wait p50/p95 |
|---|---:|---|---:|---:|---:|
| ClusterIP + pick_first | 200 / 20 | 200 / 0 | 76.16 RPS | 261.10 / 269.75ms | 202.67 / 209.16ms |
| Headless + round_robin | 200 / 20 | 90 / 110 | 133.04 RPS | 164.23 / 217.94ms | 103.75 / 160.49ms |
| ClusterIP + pick_first + max age 5s | 800 / 4, interval 20ms | 548 / 252 | 49.10 RPS | 58.16 / 63.55ms | 0.00 / 0.01ms |

kubectl 1.36.1로 도구 버전을 맞춘 뒤 같은 순서로 재실행한 결과는 다음과 같다.

| 경우 | 요청/동시성 | Pod별 요청 수 | 처리량 | latency p50/p95 | queue wait p50/p95 |
|---|---:|---|---:|---:|---:|
| ClusterIP + pick_first | 200 / 20 | 200 / 0 | 75.68 RPS | 261.44 / 274.11ms | 203.60 / 214.06ms |
| Headless + round_robin | 200 / 20 | 90 / 110 | 134.79 RPS | 170.63 / 221.22ms | 104.88 / 157.11ms |
| ClusterIP + pick_first + max age 5s | 800 / 4, interval 20ms | 56 / 744 | 49.33 RPS | 57.46 / 63.22ms | 0.00 / 0.01ms |

## 관찰

1. 기준선에서는 하나의 장수명 gRPC 채널이 보낸 200건이 모두 한 Backend Pod에 도착했다.
2. Headless Service와 `round_robin`을 함께 사용하자 같은 부하가 두 Backend Pod로 분산됐다.
3. 서버의 연결 수명을 5초로 제한하자 한 실행 안에서 두 Pod가 요청을 처리했다. 매 RPC가 균등하게 분산된 것은 아니며 548:252였다.
4. 앞의 두 경우만 부하 조건이 같다. 세 번째 경우의 처리량과 latency는 재연결 관찰용 조건이므로 다른 두 경우와 비교하지 않는다.
5. 재실행에서도 기준선은 200:0, Headless 방식은 90:110이었다. 연결 수명 제한 방식은 56:744로 더 불균등했지만 두 Pod가 모두 선택됐다. 이는 이 방식이 균등 분산을 보장하지 않는다는 해석과 일치한다.

## 해석 제한

- 2회 측정 결과이며 통계적 일반화에 부족하다.
- Pod 이름과 분포는 실행마다 바뀔 수 있다.
- 합성 처리 슬롯 때문에 관찰된 처리량과 지연 차이는 실제 시스템 성능을 예측하지 않는다.
- 두 Pod가 선택됐다는 사실만으로 정확한 GOAWAY 발생 시점이나 TCP 연결 전환 경로를 입증하지 않는다. 후속 관찰 도구가 필요하다.
