# Standalone Envoy TCP와 L7 프록시 1차 실행

## 실행 전 예측

사용자는 실행 전에 두 사례 모두 Pod별 요청 분포를 `100 / 100`으로 예상했습니다. 이유와 확신도는 별도로 제출하지 않았습니다.

## 실행 조건

- 날짜: 2026-10-06 (Asia/Seoul)
- Backend Pod: 2개
- 요청: 200 unary RPC, 동시성 20, 간격 0ms
- 클라이언트: 프로세스 하나, gRPC 채널 하나
- Envoy: `envoyproxy/envoy:v1.39.1`, upstream cluster `ROUND_ROBIN`
- 사례: `envoy-tcp` (TCP listener 50052), `envoy-l7` (HTTP/2-aware listener 50051)
- 각 사례 1회 실행. 정식 비교를 위한 반복 5회는 아직 수행하지 않았습니다.

## 관찰

| 사례 | 요청 대상 | Pod별 요청 수 | RPS | latency p50/p95/max | server queue p50/p95/max |
|---|---|---|---:|---|---|
| `envoy-tcp` | `envoy-proxy...:50052` | `backend-68648bbd59-cq2rk`: 200 | 77.15 | 256.86 / 260.82 / 271.98 ms | 200.35 / 205.25 / 208.59 ms |
| `envoy-l7` | `envoy-proxy...:50051` | `backend-68648bbd59-7bvh6`: 100; `backend-68648bbd59-cq2rk`: 100 | 146.42 | 114.81 / 162.62 / 191.22 ms | 50.65 / 101.30 / 105.22 ms |

## 해석과 한계

- `envoy-tcp`에서는 단일 downstream TCP 연결이 TCP proxy를 통과했다. TCP proxy는 연결을 터널링하므로 upstream Pod 선택은 연결 단위이며, 그 연결에 실린 RPC 200건은 한 Pod에서 처리됐다.
- `envoy-l7`에서는 HTTP/2를 처리하는 connection manager와 router가 요청 stream을 upstream으로 전달했고, 이 한 번의 실행에서는 두 Pod가 각각 100건을 처리했다.[^envoy-hcm][^envoy-lb]
- 같은 `ROUND_ROBIN` cluster 설정이라도 필터가 Backend를 선택하는 단위가 다르다. TCP proxy는 downstream 연결에 upstream 하나를 붙이고, L7 router는 HTTP 요청/stream 단위로 upstream host를 선택한다.
- 각 사례 1회뿐이다. 정확히 균등한 분포나 성능 우위를 결론내리지 않는다. 특히 서버의 합성 작업 시간과 슬롯을 사용하는 단일-node kind 측정치는 운영 환경의 성능 개선폭으로 일반화할 수 없다.
- 이 실행에서는 Channelz 연결 관찰기를 동시에 돌리지 않았다. Envoy downstream/upstream 연결 수명과 RPC별 연결 상관관계는 별도로 관측해야 한다.
